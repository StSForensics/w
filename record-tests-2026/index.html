O4M Record Tests 2026: the requirements in plain English

O4M Record Tests 2026 (v1.0) is a public comment draft of 23 requirements, C1 to C23, for checking from outside whether an AI system's activity records are complete for the scope the operator declared and have not been altered. It checks records. It does not check whether the AI system was right, safe or lawful. At this release no system can pass every in-scope requirement.

The requirements in six themes

1. Declare before you start (C1)

Before the first event, the operator writes down which policy, software, failure mode, checkpoint interval, clock tolerance and witnesses apply, which actions count as consequential, and seals that record. Without a declared scope there is nothing to check completeness against.

2. Make each record checkable (C2 to C5)

One agreed way to encode records so that anyone can recompute the hashes (C2). Numbered entries, each linked to the one before (C3). Salted commitments to inputs, outputs and tool calls, with the payloads held apart (C4). A signature on every record, with the key held apart from the application (C5).

3. Pin records in time and watch for forks (C6, C15, C16, C19)

Periodic checkpoints, time-stamped by an outside source and cosigned by witnesses (C6). A declared time tolerance (C15). Verifiers compare checkpoints, so nobody can show different histories to different people (C16). Rules for what happens when time sources are unavailable (C19).

4. Who and what acted (C7 to C10, C13)

Model identity reported on a ladder, from "someone said so" to hardware-attested (C7). Runtime attestation (C8). Authority records that trace an action to a named human or role (C9). Key issue, revocation and rotation logged (C10). Agents that spawn agents are registered at start and end (C13).

5. Did capture miss anything (C14, C17, C18, C22)

Signed counters of records received, accepted and dropped, checked against the provider's own usage figures where they exist (C14). An execution witness, compared with an independent record of the effect, such as a payment processor's (C17). Sealing before an external effect, not after (C18). A heartbeat, a rule that consequential actions wait if capture stops, and a coverage statement that shows when capture was live, degraded or absent (C22).

6. Hand over, and check the checker (C11, C12, C20, C21, C23)

An export bundle with proofs of inclusion (C11). Retention declared, and deletion only as a signed, logged event (C12). An open, reproducible verifier (C20). Verifier independence and samples drawn with public randomness (C21). Keys held outside the operator's reach, and agreement between independent verifiers (C23).

Three profiles

Few organisations can meet all 23, so every result names a profile. Profile W is for anyone using AI through a vendor that offers an admin export: it shows the records have not changed since the verifier received them, and cannot show they were complete at source. Profile F is for organisations that run their own agents on infrastructure they control. Profile P would need model providers to sign per-request usage receipts, which nobody offers today.

Where it stands

The editor has run the tests for C2, C3, C5, C11 and C18 on synthetic records, and parts of C6, C14 and C16. No result has been reproduced by anyone outside the editor. A verifier and frozen test vectors for the chain walk (T3, requirement C3) and for counters balancing (T14a, requirement C14) are in the public repository.

Results are PASS, FAIL or HOLD. A HOLD with reason codes is a useful result: it says what is still missing. Every result is unsigned, and the suite issues no certificates.

Limits we publish

  • A chain walk alone cannot detect a record that is altered with every later record recomputed. External commitments are needed for that.
  • If an operator consistently under-reports what it received, the counters still balance. Only a count the operator does not control can show it.
  • The tests check the record, not the decision the AI made.
